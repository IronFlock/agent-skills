# The repository, the build and the release

Every widget is its own git repository, `IronFlock/widget-<name>`, published to npm
as `@ironflock/widget-<name>`. Locally they are checked out side by side in an
`ironflock-widgets/` folder, next to Studio's checkout (`studio/`). All repos share
the same layout, scripts and release pipeline; the starter template
(`assets/widget-template/`) is the reference copy.

## Layout

```text
widget-<name>/
├── src/
│   ├── widget-<name>.ts            the component (one file, or a few modules)
│   ├── definition-schema.json      the config schema: the source of truth
│   ├── definition-schema.d.ts      generated by `npm run types`, committed
│   └── default-data.json           the default config of a new tile
├── demo/
│   ├── index.html                  dev page: renders the widget from src/
│   └── themes/*.json               ECharts themes, as Studio passes them
├── .github/workflows/
│   ├── ci.yml                      the gate on pull requests (types current, build)
│   ├── security.yml                security screening (pull requests, weekly)
│   └── build-publish.yml           the release: npm publish when a release merges
├── Justfile                        lint, build, merge, release-patch/-minor/-major
├── thumbnail.png, thumbnail.webp   the palette picture
├── package.json, package-lock.json
├── vite.config.ts, tsconfig.json
├── .editorconfig, .prettierrc, .gitignore, .vscode/settings.json
├── CLAUDE.md                       agent guidance: commands, architecture, decisions
└── README.md                       for people using the package
```

`dist/` is built, ignored by git and published. Generated files that the build
depends on (`definition-schema.d.ts`, widget-scada's symbol catalog) are committed,
and the CI gate (`just lint`) fails when they are stale.

## package.json

- `"name": "@ironflock/widget-<name>"`; `<name>` is lower-case kebab-case and is
  also the repo name, the folder name, Studio's `package_name` (`widget-<name>`)
  and the release name (`release widget-<name> <version>`).
- `"main": "dist/widget-<name>.js"`: the CDN serves this file for the bare package
  URL that Studio imports. No `exports`, `browser`, `jsdelivr` or `unpkg` fields
  that point elsewhere.
- `"files": ["dist", "src", "thumbnail.png", "thumbnail.webp"]`: Studio and the
  AI fetch `src/definition-schema.json` and `src/default-data.json` from the
  published package.
- `"type": "module"`, `"license": "MIT"`, `engines` as in the template.
- Plain `x.y.z` versions only. The version becomes part of a custom element name,
  and Studio compares versions numerically.
- **Scripts**, identical across the fleet: `start`, `build`, `watch`, `types`.
  New widgets also get `typecheck`, and `build` runs `tsc` first, because Vite
  strips types without checking them. No `preversion` / `version` /
  `postversion` hooks: the release writes the version with `npm version`, which
  would run them; releases run from the `Justfile`.
- Dependencies: what the widget bundles goes into `dependencies` (or
  `devDependencies`); what it leaves to the host's import map goes into
  `peerDependencies` plus `devDependencies`. `lit` stays in `dependencies` even
  when external, because the package's types import it.
- No `link`/`unlink` scripts: Studio's dev server picks up the sibling checkout by
  itself. (Older repos still point theirs at a `../RESWARM/frontend` that no longer
  exists.)

## The build

`vite.config.ts` builds a library: one ES module, `dist/widget-<name>.js`, with a
source map.

- `@rollup/plugin-replace` replaces `versionplaceholder` with
  `package.json`'s version. This is what makes the element tag and the `version`
  field carry the release number.
- `rollupOptions.external` lists exactly the shared libraries the widget takes from
  Studio's import map ([component.md](component.md#shared-libraries)).
  Everything else is bundled into the one file; no code splitting, no relative
  asset URLs.
- `define: { 'process.env.NODE_ENV': '"production"' }`, because some dependencies
  read it and browsers have no `process`.
- `resolve.alias: { tslib: 'tslib/tslib.es6.js' }`: echarts imports tslib, and the
  dev server fails on its CommonJS build.

Two older widgets (widget-mapbox, widget-textbox) still build with Rollup and
`@web/dev-server`. Their output follows the same rules.

## The demo

`npm start` serves `demo/index.html` on port 8000 and rebuilds `dist/` on every
change. The demo imports the component from `src/` and registers the tag from
`package.json`'s version. The template's demo mimics Studio: it paints the tile and
sets the `--re-*` properties on the page, switches themes the way Studio maps them
to board colours, sends a **new** config object every second, and lets you resize
the tile and switch to an empty or malformed config.

Before calling a change done, look at it there:

- the default config, `{}`, and a config with wrong types and `null` slots;
- the light and dark themes and "---" (no theme object);
- a tiny tile (about 100 × 60), a large one, and a resize while data streams;
- no errors in the browser console.

If you can drive a browser (Playwright or a browser tool), take screenshots; read
the shadow DOM after `await element.updateComplete`, because Lit renders
asynchronously. To see whether existing configs still render the same, put the
committed build next to yours: export it with
`git archive HEAD | tar -x -C <scratch>/before`, build it there, and render the
same configs with each bundle, each in its own page or iframe (both register the
same tag, and a second `define` of it throws). Keep screenshots and test pages
out of the widget repo, and stop every server you start. If you cannot drive a
browser, ask the user to look.

## Checking a change

```bash
npm run build                          # type check (where the repo has it) + bundle
npm run types && git diff --exit-code  # the generated types are current
python3 <skill>/scripts/check_widget.py .              # the standards in this skill
python3 <skill>/scripts/check_widget.py . --typecheck  # also type-check src/, for repos whose build doesn't
```

`check_widget.py` reports `ERROR`s (breaks the widget or the platform) and `WARN`ings
(standards; judge each one). In an existing widget, fix what your change touches and
report older findings instead of rewriting code you were not asked to change.

## Testing in Studio

With Studio checked out next to the widgets (`studio/` and
`ironflock-widgets/widget-<name>/` in the same folder), Studio's dev server
(`npm run dev` in `studio/`) imports every widget from its sibling folder:

- Run `npm run watch` (or `npm start`) in the widget, so `dist/` follows your edits.
  Studio imports the **built** `dist/`, not `src/`.
- Studio renders the version the board pins. The local build registers the version
  in `package.json`, so a tile only renders when its pin equals that version;
  otherwise it spins without an error. Pin the tile to the local version in the
  Widget Editor, or test on a tile that pins the current release.
- Right after a release, the local `dist/` must be rebuilt for the new version (the
  `version` hook does this; a dist built before it registers the old tag).
- The folder name must equal the package name: Studio requests
  `/widgets/<package_name>/src/...` from the sibling folder.
- A brand-new widget also needs Studio's code to know it (see
  [new-widget.md](new-widget.md)).

## Releasing

**Release only when the user asks.** A release publishes to npm, and a published
version can never be changed or removed.

`main` takes pull requests only, merged automatically once the `ci` and
`security` checks are green. From a feature branch with everything committed:

```bash
just merge            # a pull request that releases nothing
just release-patch    # a release pull request, patch: 1.2.3 → 1.2.4
just release-minor    # minor: 1.2.3 → 1.3.0
```

What `just release-patch` does (the shared `scripts/pr.sh` of IronFlock/workflows):

1. Refuses uncommitted changes, takes the next version from `main`'s
   `package.json` and writes it to `package.json` and the lockfile
   (`npm version --no-git-tag-version`).
2. Commits that bump as `release widget-<name> <version>` on top of the branch
   (on an up-to-date `main`, on a new branch `release/<version>`), pushes it and
   opens the pull request with auto-merge.
3. CI checks it like any pull request, plus a dry run of the release
   (`npm publish --dry-run`).
4. The merge runs `.github/workflows/build-publish.yml`: build, `npm publish`
   with npm's trusted publishing (OIDC, no token; the trusted publisher names
   this file), then the release GitHub App sets the bare-version tag (`1.2.4`)
   and creates the GitHub release. `just release-patch` waits for that run and
   ends on the updated `main`.

Rules:

- Never `npm publish` from a laptop (the only exception is the very first version
  of a new package), never create or move tags by hand, never edit `version` in
  `package.json` by hand.
- Use patch for fixes and small additions, minor for new capabilities. There are no
  breaking releases: boards keep old configs ([config-schema.md](config-schema.md#changing-a-schema-without-breaking-boards)).
- If the release run fails after the merge, re-run it when the cause was
  transient (a version already on npm is not published again); otherwise fix the
  cause and release the next version. Don't delete or reuse a tag.

## After a release

A new version on npm changes nothing on any board yet. Studio's pinned dependency
(what appliances bundle) and the platform database's current version per widget
(what new tiles and the AI use) have to follow, in that order. For a fix of a crash
or an unreadable rendering, Studio can also raise the minimum version that older
pins render on cloud. Existing tiles keep their pinned version until someone picks
the new one in the Widget Editor. If the root `description` or `aiSelection`
changed, this plugin's widget catalog is rebuilt too.

These steps are in IronFlock's internal repositories and are deployed by the
platform team. IronFlock developers find them, with every file, in the internal
runbook `docs/INTERNAL-widget-platform.md` of the deployments repository. Prepare
them only when the user asks, never deploy, and tell the user which of them the
release needs.

## Documentation and thumbnails

- **CLAUDE.md** is for agents working in the repo: the commands, the architecture
  (how `inputData` flows to the screen), and every non-obvious decision with its
  reason. Keep the shared sections (commands, the versioned tag, theming, the
  `aiSelection` rules) in the fleet's wording, and update the file in the same
  change as the code it describes.
- **README.md** is for people: what the widget shows, how to install and register
  it (build the tag from the installed version, never a hard-coded one), its
  settings at a glance, theming, and the development commands. widget-doughnut's
  README is the model.
- **Thumbnails** are what the board editor's palette shows. Take a screenshot of
  the demo tile with representative data, cropped to 4:3, and save it as
  `thumbnail.png` (1600 × 1200) and `thumbnail.webp` (400 × 300; the palette
  shows it at most 200 px wide). For example:

  ```bash
  sips -z 1200 1600 shot.png --out thumbnail.png
  cwebp -q 85 -resize 400 300 shot.png -o thumbnail.webp
  ```

  Never ship a thumbnail copied from another widget.
